Settle system design

A trust layer for deals struck in social chats: check the chat, lock what was agreed, take payment through PayPal, and release “safe to ship” only on money PayPal has confirmed.
Version 0.1, draft
16 October 2026
PayPal AI Hackathon

Problem and scope

US and UK buyers and sellers agree deals with strangers in Instagram DMs, Facebook Marketplace and WhatsApp. There is no checkout and no record of the agreement, so common scams work: fake payment screenshots, “ship first” pressure, overpayment refunds and off-platform payment links.

Settle checks a pasted chat for warning signs, turns it into a deal card both sides confirm, takes payment with PayPal, and gates shipping on confirmed money. In a dispute it drafts the seller’s evidence; the seller decides what is sent.

Design principles

  • The server owns money. Orders are built from the locked deal card, never from browser input. Amount, currency and payee are checked again after payment.
  • Only PayPal confirms payment. A verified webhook plus a fresh order lookup. Client callbacks, screenshots and emails are never evidence.
  • Fail closed. Every error resolves to Hold or Review. The UI says “no warning signs found”, never “safe deal”.
  • AI adds caution, never permission. Jev can raise warnings; it cannot approve shipping or send a dispute response.
  • Everything leaves a receipt in an append-only log.

Architecture

All PayPal and Jev calls run on the server; the browser never sends an amount the server trusts. Webhooks (amber) are the only path by which payment becomes fact.

The ship gate

Six checks, one green path. A timeout, a malformed body, an unknown order or a PayPal outage all land in Hold; anything that means “paid, but not what was agreed” lands in Review. Jev feeds only the last check, so it can stop a shipment but never start one.

Payment and fulfilment sequence

  1. Check. Seller or buyer pastes the chat. Server redacts it, runs dealCheck, and returns warnings plus a draft deal card. Receipt written.
  2. Confirm. Each side opens a signed link and confirms the card. When both have confirmed, the card is locked and its hash stored.
  3. Connect seller. Seller signs in with PayPal; Settle stores their merchant ID on the deal as the expected payee.
  4. Create order. The buyer’s PayPal button calls the server, which builds the order from the locked card: amount, currency, payee, and the deal ID as custom_id.
  5. Capture. After the buyer approves, the server captures. The UI shows “payment received, waiting for PayPal to confirm”, not “safe to ship”.
  6. Gate. The capture webhook runs the ship gate above. The deal page and dashboard show the outcome and its reasons.
  7. Ship. The seller enters tracking; Settle adds it to the PayPal order so it counts as proof of delivery.
  8. Dispute. A dispute webhook (verified the same way) runs disputePlan. The seller edits and approves the draft; only then is evidence submitted.

Security and privacy

  • Secrets live in .env.local or Render env vars; never in git, logs or the browser.
  • Deal links carry random tokens; only their hashes are stored.
  • Raw chat is redacted before storage and model calls; prices and links are parsed in code.
  • The dashboard AI route gets auth and a rate limit before it is public.

Deployment and testing

  • Hosting: one Render web service (Node 22) and Render Postgres, defined in render.yaml. The webhook URL is registered in the sandbox app and its ID set as PAYPAL_WEBHOOK_ID.
  • Tests: npm test runs unit tests with Jev and PayPal mocked, covering redaction, parsing, every gate branch and idempotency. npm run jev:eval scores Jev questions against labelled chats.
  • End to end: Playwright drives a sandbox checkout and captures demo screenshots.

Risks to check before judging

Free-tier services sleep when idle, so the first request and the first webhook may be slow; PayPal retries failed webhooks, and the gate stays on Hold until one lands. Free Postgres may expire after a fixed period. Sandbox access tokens last about nine hours. All three are verified in Phase 6.
